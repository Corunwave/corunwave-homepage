## Framework caveat (read before writing Next.js code)

This project is on **Next.js 16.4.2 + React 19.3.0** — see `AGENTS.md`'s `BEGIN:nextjs-agent-rules` block. APIs, conventions, and file structure may differ from older Next.js knowledge. When in doubt, consult `node_modules/next/dist/docs/`. The `AGENTS.md` wrapper block is regenerated by `next dev` — don't bother removing it from diffs.

`next.config.ts` enables these non-default features:
- `reactCompiler: true` (the `babel-plugin-react-compiler` devDep is wired for this — don't manually memoize)
- Turbopack CSS loader routes `*.css` through `@tailwindcss/turbopack`.

TypeScript path alias: `@/*` → `./*` (repo root).

## Styling — enforced rules

From `AGENTS.md`, these are hard constraints, not preferences:

- **All styles live in `app/globals.css`.** Design tokens, component styles, media queries, animations — all of it.
- **Do not create** component CSS files, CSS Modules, Sass files, `style` props, `<style>` tags, styled-jsx, or any CSS-in-JS. Components apply styles via `className` referencing classes defined in `globals.css`.
- Tailwind tokens and custom utilities are declared inside `globals.css` under `@theme static` / `@theme inline`. Don't add new ad-hoc values via Tailwind arbitrary-value utilities (`w-[237px]`, etc.) — add a token first.
- Don't split styles into separate files to work around dev-server or cache issues. Don't refactor existing style structure unless asked.

### Design token convention

Spacing and radius token names encode **pixels, not Tailwind's 4px scale** — e.g. `--spacing-24` is `24px`. Tailwind spacing utilities are prefixed with `space-` (`gap-space-24`, `p-space-16`) specifically to preserve the normal meaning of `p-4` / `gap-6`. When adding tokens, follow this pattern.

Dark mode is explicit opt-in via `[data-theme="dark"]` — do not auto-enable via `prefers-color-scheme`.

## Fonts

- **Admin-controlled:** the `typography` global (CEO only) sets `data-font-scale` / `data-body-font` / `data-heading-font` on `<html>` in `app/(site)/layout.tsx`; the `html[data-*]` rules in `globals.css` apply them. Text size scales through the root `font-size` because every font-size/line-height token is rem — keep new text tokens in rem so they scale too. A new font option needs: registration in `fonts.ts` + `<html>` class, an entry in `payload/globals/Typography.ts`, and a matching `html[data-*-font]` rule.

- **Default (body, nav, UI):** Pretendard — inherited through `body`'s `--font-family-body`, or applied with Tailwind's `font-sans`.
- **Accent only:** A2Z — applied with `font-emphasis`. Currently binds A2Z Regular. Don't swap body font globally to A2Z.
- All font faces are local (`public/fonts/*.woff2`), declared in `public/fonts/fonts.ts` with `next/font/local`, and must be registered via each export's `.variable` class on `<html>` in `app/layout.tsx`. If you add a weight, follow the same path.
- Centralize font family values in `globals.css` under `--font-family-body` / `--font-family-emphasis`. Don't hardcode font-family in component styles.
- When translating Figma designs: preserve these two roles even if the Figma source uses Noto Sans KR or similar. Don't add external font downloads for body/accent roles.

## Architecture

Next.js App Router with a single root layout composing a shared header + footer around every page:

```
app/
  layout.tsx          # RootLayout — registers font variables on <html>,
                      #   wraps children with HeaderNavbar + Footer.
  page.tsx            # Home route.
  globals.css         # Single stylesheet (see Styling section).
  _components/
    commons/          # Shared layout components (not route-mapped — _ prefix).
      header/HeaderNavbar.tsx
      footer/Footer.tsx
      buttons/LinkButton.tsx
      tabs/Tabs.tsx
public/
  fonts/              # Local .woff2 files + fonts.ts exports.
  images/             # Logos, 3D illustrations, etc.
```

The `_components` folder is Next.js's convention for a private folder (underscore prefix) that is excluded from routing. New shared components belong under `app/_components/commons/<group>/`.

### Backend / API

Server logic lives in `backend/<domain>/` as clean architecture (`domain` → `application` → `infrastructure`, wired in a `*Container.ts`), exposed through thin Route Handlers under `app/api/`. The browser side calls them through `app/_lib/api/` (axios) and a hook in `app/_hooks/`. Storage goes through the Payload Local API (collections in `payload/collections/`); no separate ORM or `supabase-js`. **When creating or wiring any API, use the `api-implement` skill** (`.claude/skills/api-implement/SKILL.md`); the contact form (`backend/contact/`, `app/api/contact/route.ts`) is the reference implementation.

### CMS (Payload)

Payload 3 is embedded in this app (`/admin`, REST under `/api`); data lives in the `payload` schema of the Supabase Postgres, files in the Supabase Storage bucket via S3. Site routes sit in the `app/(site)/` group and the admin in `app/(payload)/`, each with its own root layout.

- Config: `payload.config.ts`; collections in `payload/collections/`, globals in `payload/globals/`, roles/access in `payload/access/roles.ts` (`ceo` is a single fixed account).
- The site reads CMS data only through `app/_lib/cms/*` (`unstable_cache` + tags in `payload/hooks/revalidate.ts`); collection/global `afterChange` hooks call `revalidateTag`.
- In CMS: `contact-inquiries` (the contact form's storage; list/status/resend-mail in the admin, only `/api/contact` can create), `typography` (global text scale + body/heading font roles), `site-settings` (footer, contact CTA), `legal-documents`, `documents` (download PDFs, `slot` links portfolio buttons), `media`, and the page globals `home`, `about`, `solutions`, `partner-strategy`. - News: the `news` collection (drafts/autosave, Lexical body with images/PDF, required `tag` select `internal|external|tech`, title ≤ 50 chars, SEO; a future `publishedAt` hides a post until then, there is no job queue). The thumbnail falls back to the first body image on save. Read is public (published only), create/update/delete are `ceo`/`editor`. The CRUD API is Payload's own REST at `/api/news` (do not add `app/api/news` — it would shadow the admin's REST calls); the browser calls it through `app/_lib/api/newsApi.ts` + hooks in `app/_hooks/` (`useNewsList`, `useNews`, `useCreateNews`/`useUpdateNews`/`useDeleteNews`). **The site has no news pages yet** — the `/news` route is still a placeholder.
- Not in CMS yet: header nav, contact page copy, SEO defaults.
- Page globals keep editable text only. Images, colors and layout keys stay in code: loaders in `app/_lib/cms/*` merge CMS rows with `app/_content/*.ts` by `key`/`id` (`normalize.ts` converts `{line}` rows back to strings and `key` back to `id`). `app/_content/*.ts` therefore remains the type source, the layout constants and the seed defaults — editing text there no longer changes the site.
- Fixed-set rows (`fixedRowsField`) can't be added or removed in the admin because each is tied to a code-owned image/style.
- Postgres identifiers cap at 63 chars; deeply nested arrays need `dbName` (see `bulletsField`).
- `npm run seed` creates missing CMS data from `app/_content` (never overwrites). `payload` CLI commands (`generate:types`, migrations) currently crash on undici under tsx; bundle with esbuild as the seed script does. After adding or changing an admin component or a Lexical feature, run `npm run generate:importmap` (writes `app/(payload)/admin/importMap.js`) or the admin breaks in production builds.

### Header behavior (`HeaderNavbar`)

`HeaderNavbar` is a client component with two coordinated behaviors driven by CSS variables read from `:root`:

1. **Scroll-triggered theme change.** Reads `--header-scroll-threshold` on mount; toggles `data-light` on the `<header>` once scroll passes the threshold. The light surface styles live in `.site-header[data-light="true"]` in `globals.css`.
2. **Responsive mobile panel.** Reads `--header-mobile-breakpoint` and uses `matchMedia` to auto-close the mobile menu when the viewport grows beyond it. Click-outside and Escape also close the panel.

The component accepts `appearance="light"` (force light surface for contact-style pages) and `scrolledOverride` (future hero pages can supply their own progress signal). Keep the JS-readable CSS variables in `globals.css` in sync with the media-query literals below them.
